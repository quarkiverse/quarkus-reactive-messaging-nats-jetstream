= Quarkus NATS Jetstream Client

include::./includes/attributes.adoc[]

This extension provides a reactive client for https://docs.nats.io/nats-concepts/jetstream[NATS JetStream] inside a Quarkus App, in JVM and Native mode. It does not depend on Reactive Messaging.

NOTE: The client and configuration were significantly reworked after version `3.38.0`. If you are using `3.38.0`
or earlier, see the
https://github.com/quarkiverse/quarkus-reactive-messaging-nats-jetstream/blob/3.38.0/docs/modules/ROOT/pages/index.adoc[3.38.0 documentation]
instead of this page.

== Installation

Add the `io.quarkiverse.reactivemessaging.nats-jetstream:quarkus-nats-jetstream-client` extension to your build file.

For instance, with Maven, add the following dependency to your POM file:

[source,xml,subs=attributes+]
----
<dependency>
    <groupId>io.quarkiverse.reactivemessaging.nats-jetstream</groupId>
    <artifactId>quarkus-nats-jetstream-client</artifactId>
    <version>{project-version}</version>
</dependency>
----

To consume and publish through SmallRye Reactive Messaging channels, use the `quarkus-messaging-nats-jetstream` extension instead, which builds on this one.

== Injecting the JetStream `Client`

Each configured datasource (see the "Datasources" section below) is exposed as an `@ApplicationScoped` CDI bean of
type `io.quarkiverse.reactive.messaging.nats.jetstream.client.Client`. The extension creates and registers these
beans itself - there is nothing to produce or configure - and closes them automatically on application shutdown.
You can inject a `Client` wherever you need direct access to the NATS JetStream API, for example to reach the
Key/Value or Object store (see below) or to publish/subscribe.

For the *default* (unnamed) datasource, inject it directly with a plain, unqualified `Client`:

----
@Inject
Client client;
----

For an additional, *named* datasource configured under `quarkus.messaging.nats.data-sources.[datasource-name]`,
qualify the injection point with `@Identifier("[datasource-name]")`:

----
import io.smallrye.common.annotation.Identifier;

@Inject
@Identifier("orders-db")
Client client;
----

If the datasource to use is only known at runtime, inject `@Any Instance<Client> clients` and resolve it by name
yourself, for instance with SmallRye's `CDIUtils.getInstanceById(clients, datasourceName)`.

== Using NATS Key/Value store
If you want to use the Key/Value store in NATS, then configure your application as follows:

----
quarkus.messaging.nats.connection.servers=nats://localhost:4242
quarkus.messaging.nats.connection.username=guest
quarkus.messaging.nats.connection.password=guest

# Creates a "test" bucket stored in memory. This part is optional. If you already have created a bucket on NATS
# then this configuration is redundant.
quarkus.messaging.nats.key-values.test.bucket-name=test
quarkus.messaging.nats.key-values.test.storage-type=Memory
quarkus.messaging.nats.key-values.test.description=Test bucket
----

Then your application can use the Key/Value store like this, through `Client.keyValue(bucketName)`:

----
@Path("/key-value")
@RequestScoped
class KeyValueStoreResource {
    private final Client client;

    @Inject
    public KeyValueStoreResource(Client client) {
        this.client = client;
    }

    @GET
    @Path("{key}")
    public Uni<byte[]> getValue(@PathParam("key") String key) {
        return client.keyValue("test").get(key).onItem().transform(entry -> entry.value().orElse(null));
    }

    @PUT
    @Path("{key}")
    @Consumes("application/octet-stream")
    public Uni<Void> putValue(@PathParam("key") String key, byte[] value) {
        return client.keyValue("test").put(key, value).replaceWithVoid();
    }

    @DELETE
    @Path("{key}")
    public Uni<Void> deleteValue(@PathParam("key") String key) {
        return client.keyValue("test").delete(key);
    }
}
----

=== Per-entry TTL

Buckets configured with `limit-marker-ttl` accept per-entry TTLs (requires NATS server 2.11+). `create` and `purge`
have overloads taking a `Duration`:

[source,java]
----
client.keyValue("cache").create(key, value, Duration.ofMinutes(5));
client.keyValue("cache").purge(key, Duration.ofMinutes(1));
----

The server only supports whole-second TTLs, so the duration is rounded up to the next second.

== Using NATS Object Store
If you want to use the Object store in NATS, then configure your application as follows:

----
quarkus.messaging.nats.connection.servers=nats://localhost:4242
quarkus.messaging.nats.connection.username=guest
quarkus.messaging.nats.connection.password=guest

# Creates a "test" object store. This part is optional. If you already have created the bucket on NATS
# then this configuration is redundant.
quarkus.messaging.nats.object-stores.test.bucket-name=test
quarkus.messaging.nats.object-stores.test.description=Test object store
----

Then your application can use the Object store like this, through `Client.objectStore(bucketName)`:

----
@Path("/object-store")
@RequestScoped
class ObjectStoreResource {
    private final Client client;

    @Inject
    public ObjectStoreResource(Client client) {
        this.client = client;
    }

    @GET
    @Path("{name}")
    public Uni<byte[]> getObject(@PathParam("name") String name) {
        return client.objectStore("test").get(name).onItem().transform(ObjectEntry::data);
    }

    @PUT
    @Path("{name}")
    @Consumes("application/octet-stream")
    public Uni<Void> putObject(@PathParam("name") String name, byte[] data) {
        return client.objectStore("test").put(name, data).replaceWithVoid();
    }

    @DELETE
    @Path("{name}")
    public Uni<Void> deleteObject(@PathParam("name") String name) {
        return client.objectStore("test").delete(name).replaceWithVoid();
    }
}
----

== Serializing Java Objects

By default, Java objects are serialized using `java.io.*` streams. If either the `quarkus-jackson` or
`quarkus-jsonb` dependency is present, objects are serialized as JSON instead.

To use a custom serializer, set the build-time property `quarkus.messaging.nats.serializer` to the
fully-qualified class name of a class that implements
`io.quarkiverse.reactive.messaging.nats.jetstream.client.message.Serializer`. The default value is
`io.quarkiverse.reactive.messaging.nats.jetstream.client.message.JacksonSerializer`.

[source,properties]
----
quarkus.messaging.nats.serializer=com.example.MySerializer
----

== Open Telemetry Tracing
To use Open Telemetry tracing, add the `quarkus-opentelemetry` dependency. Spans follow the
https://opentelemetry.io/docs/specs/semconv/messaging/messaging-spans/[OpenTelemetry messaging semantic conventions]
as implemented by the OpenTelemetry instrumentation API bundled with Quarkus, so they look like the spans of the
other Quarkus messaging extensions.

[cols="2,1,3",options="header"]
|======
| Span | Kind | Created when
| `{subject} publish` | `PRODUCER` | A message is published. The span covers the publish until JetStream acknowledged it, and
records the failure when publishing fails.
| `{subject} receive` | `CLIENT` | A message is pulled on demand with `Client.next` or `Client.fetch`. The span ends as
soon as the message is received.
|======

The trace context of the publisher is propagated in the message headers. It is the parent of the `receive`
spans, and is also added to them as a span link.

Besides the standard `messaging.*` attributes (`messaging.system` is `nats`, `messaging.destination.name` is the
subject, `messaging.message.id` the message id and `messaging.message.conversation_id` the request/reply correlation
id), spans carry NATS JetStream specific attributes:

* `messaging.nats.stream.name`
* `messaging.nats.consumer.name`, `messaging.nats.stream.sequence`, `messaging.nats.consumer.sequence` and
`messaging.nats.message.delivered_count` on received messages

The message payload is not recorded, since it may contain sensitive data and can be arbitrarily large. It can be
recorded as the `messaging.nats.message.payload` attribute with:

[source,properties]
----
quarkus.messaging.nats.trace-payload=true
----

.Thread pool configuration
Every datasource's `Client` owns a thread pool, shut down when the client is closed. The blocking calls of the client
run on this pool: publishing a message (sending it and waiting for the JetStream acknowledgement), `next` and `fetch`,
and managing streams, consumers, key-value stores and object stores. They therefore do not take the threads of the
Quarkus worker pool. Threads are started on demand up to the maximum size before tasks are queued.

Alternatively, with `quarkus.messaging.nats.thread-pool.virtual-threads=true`, every blocking call runs on a new
virtual thread. The pool then has no size limit and no queue, so the size, queue and keep alive properties are
ignored.

[cols="4",options="header"]
|======
| Property Name | Description | Type | Default Value
| quarkus.messaging.nats.thread-pool.virtual-threads | Whether every blocking call runs on a new virtual thread instead of a pooled platform thread | Boolean | false
| quarkus.messaging.nats.thread-pool.core-size | The number of threads kept in the pool, even when they are idle | Integer | 1
| quarkus.messaging.nats.thread-pool.max-size | The maximum number of threads in the pool | Integer | 8 x available processors
| quarkus.messaging.nats.thread-pool.queue-size | The maximum number of tasks waiting for a thread when all threads are busy. A publish submitted when the queue is full is rejected, and the message is not acknowledged. | Integer | unbounded
| quarkus.messaging.nats.thread-pool.keep-alive | How long a thread above the core size may stay idle before it is stopped | Duration | 30s
| quarkus.messaging.nats.thread-pool.shutdown-timeout | How long closing the client waits for running tasks to complete before interrupting them | Duration | 10s
|======

=== Datasources

The connection, streams, consumers, key-value stores and object stores configured directly under
`quarkus.messaging.nats.*` (as shown in the table above, and in the tables below) belong to the *default*
datasource. For symmetry with named datasources, the same properties can also be set under
`quarkus.messaging.nats.default.*` (for example `quarkus.messaging.nats.default.connection.servers`) - both
spellings are aliases for exactly the same configuration, so use whichever reads better in your application.

Additional, named datasources - each with their own connection, streams, consumers, key-value stores and object
stores - are configured under `quarkus.messaging.nats.data-sources.[datasource-name]`, using the same property
shape as the default datasource:

----
quarkus.messaging.nats.data-sources.orders-db.connection.servers=nats://orders-nats:4222
quarkus.messaging.nats.data-sources.orders-db.streams.orders.name=orders
quarkus.messaging.nats.data-sources.orders-db.streams.orders.subjects=orders.*
----

Every configured datasource - default and named - gets its own `Client` CDI bean; see "Injecting the JetStream
`Client`" above.

Each entry in the `quarkus.messaging.nats.streams` map is created (if absent) with `[stream-name]` as its map key; `name` must be set explicitly and is conventionally the same value as `[stream-name]`.
